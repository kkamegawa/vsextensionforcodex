# ADR-012: Remote App Server transport

- Date: 2026-09-13
- Status: Accepted
- Tracking: Codex App Server update remote connection child Issue

## Decision

- Keep local stdio as the default and add an explicitly enabled WebSocket transport for an already running remote server.
- Accept `wss`; allow `ws` only for loopback. Use a token file for bearer authentication and never expose its contents. Certificate validation cannot be disabled.
- A local connection owns its child process. A remote connection owns only the socket and presents reconnect instead of restart.
- Serialize connection transitions, separate health checks from RPC availability, and retry read-only RPCs with bounded exponential backoff and jitter.

## Consequences

Remote lifecycle stays outside the extension while transport policy is shared by local and remote clients.

## Amendment (2026-09-23, PR #157 review)

- Task: Issue #151 (remote transport) as implemented in PR #157.
- Both transports share one server-request dispatcher, so request ownership, error shaping, and response suppression after close cannot diverge. Notifications are delivered one at a time in wire order on every transport. Streaming deltas and turn lifecycle events depend on that order.
- The Worker observes the remote transport's `Closed` event and reports `Degraded` with a reconnect action, because a remote connection has no child process `Exited` signal.
- CI builds with the pinned contract executable. The latest stable release runs only a non-blocking start-and-initialize smoke test, because a build that used the latest executable would fail once it differed from the pinned schema contract.
- Reason: these are corrections from the review, not new direction. They implement the existing decisions (shared transport behavior, distinct remote status, pinned contract).

## Amendment (2026-09-30, PR #157 second review)

- Task: Issue #151 (remote transport) as implemented in PR #157.
- The remote profile editor is part of PR #157 instead of a later Issue #151 change. A connection-target flyout in the tool window edits saved profiles and applies one on explicit request (design.md section 12). Reason: without a reachable editor, remote transport cannot be used from the normal UI, so the feature would ship incomplete.
- A remote connection requires both `localRoot` and `serverRoot`. The Worker refuses the connection as `Degraded` otherwise, so an unmapped local path never reaches the server. Reason: path mapping is the only way local paths become valid on the server; this tightens, and does not change, the existing mapping decision (ADR-013).
- A remote connection loss is published under the connection-transition gate and only when no newer connect, restart, or dispose superseded that connection. Reason: a delayed close must not overwrite a newer `Ready` state; this implements the existing serialized-transition decision.
- The remote connection ships as a Preview. The flyout heading and README say so, and they list what is not available yet: health checks, bounded retry, and state isolation across accounts and endpoints (Issues #151 and #152). Reason: local stdio is release-ready, while those remote items remain open. Labeling the feature keeps the release honest without withholding a working opt-in feature.

## Amendment (2026-10-01, Issue #151 design review)

- Status: Accepted (2026-10-02, maintainer approval in [PR #161](https://github.com/kkamegawa/vsextensionforcodex/pull/161)).
- Task: Complete the Issue #151 secure remote-connection behavior using `doc/secure-remote-connection-design.md` as the normative design. The accepted amendments above remain the record of the behavior available at their dates. In particular, the 2026-09-30 statement that health diagnostics and bounded retry were unavailable records the then-current implementation gap; it does not pre-approve this amendment.
- Decision: Put endpoint validation in the pure Contracts project and have Protocol, Worker, and Extension share it. Permit `ws` only for syntactically eligible canonical loopback forms; pure policy does not perform DNS verification. Reject unspecified literal destinations and credential/query/fragment URI parts for every scheme, including `wss`. For `ws`, additionally reject DNS aliases, terminal-dot localhost, localhost subdomains, and all non-loopback forms. The Worker resolves exact localhost before token access, verifies every answer is loopback, and pins only that verified authority and direct connection attempt. Do not apply `ConnectCallback` pinning to remote `wss` IP literals or proxy targets. Use one Worker-lifetime proxy resolver for WebSocket and health traffic, retain platform TLS, disable redirects/cookies/default credentials, and never fall back from proxy failure to direct networking. Only verified-loopback literals and exact-localhost endpoints bypass the proxy; health probes bypass it only when derived from those same verified local endpoints.
- Decision: Validate profile metadata at Save without opening the token file. Keep the active applied-profile fingerprint and generation in memory. Before reconnect, compare the latest saved profile to that exact snapshot and reject unsaved or changed metadata. Serialize all same-instance profile/settings mutations—selection persistence, Save, rename, enable/disable, delete, and explicit switch to local—with snapshot validation and RPC dispatch; revalidate the immutable reconnect request in the Worker before token read, socket stop, or send. Token contents are read only by the Worker from an absolute local file immediately before each handshake, with a 16 KiB bound, strict UTF-8, optional BOM, and bounded RFC 6750 token syntax. Do not inspect or change ACLs. Keep secret-redactor registrations in reference-counted leases until all sockets, queued diagnostics, callbacks, and pending operations are retired; redact before enqueue. Both the Worker and Extension writers append to the shared `diagnostics.log` and redact immediately before append; every other existing output writer also redacts before writing. Avoid awaiting a callback that needs the transition gate while holding it: suppress/unsubscribe and dispose under the gate, then track and drain queued close callbacks after releasing the gate before releasing the lease, or use equivalent callback-owned leases. Do not add telemetry.
- Decision: Bound remote startup by one monotonic 45-second deadline with separate token-read, WebSocket, initialize, and startup account-read stage caps. Preserve RPC Ready when account status is SignedOut or an account-read failure is classified as Unavailable; transport close, caller cancellation, and the overall startup deadline retire the candidate. Health diagnosis uses unauthenticated concurrent root `/healthz` and `/readyz` GETs under a five-second total deadline, with no response-body read. For routed WebSocket paths, report authority-root scope and unverified route coverage. Health never changes RPC state or feature availability. Set the .NET 8 WebSocket `KeepAliveInterval` to 30 seconds; unsolicited PONG frames are not peer-liveness proof and `KeepAliveTimeout` is unavailable. Use a 30-second inbound-silence watchdog that observes every valid parsed response, notification, and server request via an inbound-activity sequence. If a 10-second probe times out after the sequence advanced, skip the second probe and restart the normal 30-second idle wait; otherwise issue one immediate second `account/read(refreshToken: false)` probe with a 10-second deadline. Watchdog probes send once without overload retry. Retire only the captured current-generation socket after two silent timeouts and never auto-reconnect or replay a mutation.
- Decision: Replace the caller-controlled retry boolean with `SendReadOnlyRequestAsync`, which owns the exact method allowlist and the `account/read.refreshToken` and `skills/list.forceReload` predicates; do not add full-shape validation for the other six known read-only methods. Retry only completed `-32001` responses for `account/read` with explicit false `refreshToken`, the specified account/model/thread/permission/MCP reads, and `skills/list` only with explicit false `forceReload`; other values, methods, and all mutations send once. Allow three retries after the first request with 250/500/1000 ms base waits, ±20% jitter, one existing per-call monotonic deadline, cancellation, and generation binding. Keep future history and attachment reads outside the allowlist until separately evidenced.
- Decision: Advance the bundled Extension/Worker contract atomically from v16 to the next available contract version (v17 if the base remains unchanged); rebase to the latest version before merge and reject mismatched binaries. Distinguish local `worker/restart` from remote `worker/reconnect` before any stop/send. Return typed `-32051` connection-operation rejection reasons. Update the Preview guidance when diagnostics and retry are implemented, while retaining the Issue #152 account/principal isolation limitation.
- Reason: the earlier plan already requires endpoint security, independent health/RPC state, bounded read-only retry, and distinct local/remote ownership. This amendment specifies the cross-layer rules needed to make those commitments safe: it prevents endpoint-policy drift, DNS rebinding, stale-profile reconnect, secret leakage through asynchronous diagnostics, false health conclusions, retry of discovery/cache-changing inputs, and silent-peer state from leaking across generations. No cross-process cache/account/principal isolation or Issue #153 recovery guarantee is added.
